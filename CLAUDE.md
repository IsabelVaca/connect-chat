# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"RoomieMatch" (repo name `connect-chat`) is a roommate-matching web app: discovery/swipe screen, mutual matches list, per-contact chat, and a profile/preferences screen. It is built and synced through [Lovable](https://lovable.dev) — commits pushed to the connected branch sync back into the Lovable editor, so keep the branch buildable (see Git rules below).

## Commands

```sh
npm i           # install deps (package-lock.json is present; bun.lock also exists — see note below)
npm run dev     # start Vite dev server (TanStack Start SSR)
npm run build   # production build
npm run build:dev  # build in development mode
npm run preview   # preview a production build
npm run lint    # eslint .
npm run format  # prettier --write .
```

There is no test suite/framework configured in this repo (no `test` script, no test files).

Note: both `package-lock.json` and `bun.lock` exist. `bunfig.toml` configures a 24h supply-chain guard on new package versions (`minimumReleaseAge`), so this project is normally managed with `bun install`/Lovable tooling; use `npm i`/`npm run dev` for plain local dev as documented in the README.

## Architecture

- **Framework**: TanStack Start (React 19 + TanStack Router) with SSR, via `@lovable.dev/vite-tanstack-config`. That package already wires up TanStack devtools, `tanstackStart`, `viteReact`, `tailwindcss`, `vite-tsconfig-paths`, the `@` path alias, and Nitro (Cloudflare target) — **do not** re-add any of these plugins manually in `vite.config.ts` (see the warning comment at the top of that file).
- **Routing**: file-based routing under `src/routes/`, per the conventions documented in `src/routes/README.md`:
  - `index.tsx` → `/`, `matches.index.tsx` → `/matches`, `matches.$contactId.tsx` → `/matches/:contactId`, `profile.tsx` → `/profile`.
  - `__root.tsx` is the only root layout/app shell (renders `<html>`, `<head>`, wraps everything in `QueryClientProvider` + `AppStateProvider`, and must preserve `<Outlet />`).
  - Do **not** create `src/pages/`, `_app/` folders, or `app/layout.tsx` — those are Next.js/Remix patterns, not TanStack Start.
  - `src/routeTree.gen.ts` is auto-generated by the router plugin — never edit it by hand.
- **Global state**: `src/lib/app-state.tsx` exposes `AppStateProvider`/`useAppState()` (React context) holding: `location`, `conversations` (per-contact message lists), `contacts`, `userProfiles`, `selectedProfileId` (drives the `DetailedProfileView` overlay rendered from `__root.tsx`), and actions `sendMessage`, `setLocation`, `setSelectedProfileId`, `startChat`. There is no backend — everything is client-side mock state seeded from `src/lib/mock-data.ts` and lost on reload.
- **Mock data** (`src/lib/mock-data.ts`) is the single source of truth for `contacts`, `mutualMatches`, `conversations`, and `userProfiles` (richer profile objects used by Discovery/DetailedProfileView, keyed by the same ids as `contacts`). When wiring new UI, prefer extending this file over inventing parallel data shapes.
- **Server plumbing** (`src/server.ts`, `src/start.ts`): both exist purely to make sure SSR errors never leak an unstyled 500 — they catch h3-swallowed errors and render `renderErrorPage()` from `src/lib/error-page.ts` instead. `src/start.ts` also re-registers `createCsrfMiddleware` for server functions (TanStack Start skips this automatically once a custom `src/start.ts` is present, so it must be added back explicitly). Don't strip this error-handling/CSRF wiring when touching these files.
- **Error reporting**: `src/lib/error-capture.ts` + `src/lib/lovable-error-reporting.ts` feed into the root route's `ErrorComponent`/Lovable's error tracking — client-side errors are captured and reported with a `boundary` tag.
- **UI kit**: `src/components/ui/*` is the shadcn/ui component set (config in `components.json`: style `new-york`, Tailwind CSS variables, `lucide-react` icons, path aliases `@/components`, `@/lib`, `@/hooks`, `@/ui`). Prefer reusing/composing these primitives (and `cn()` from `src/lib/utils.ts` for class merging) instead of writing new low-level UI components.
- **Styling**: Tailwind v4 via `@import "tailwindcss"` in `src/styles.css`, which also defines the entire RoomieMatch design-token system (`--color-surface`, `--color-brand`, `--color-teal`, typography scale like `font-headline-lg-mobile`, spacing tokens like `--stack-md`/`--container-margin`, etc.) inside an `@theme inline` block. **Components must never hardcode raw colors/spacing** — always use the existing semantic tokens/utility classes (`bg-surface`, `text-on-surface`, `text-brand`, `px-container-margin`, etc.). Icons are Google "Material Symbols Outlined" (loaded via a `<link>` in `__root.tsx`'s `head()`), used as `<span className="material-symbols-outlined">icon_name</span>`, with `icon-filled` as a modifier class for the filled variant.
- **App shell pattern**: most screens render `<TopAppBar />` + page content + `<BottomNav />` (fixed bottom tab bar with routes `/`, `/matches`, `/profile`). The contact conversation screen (`matches.$contactId.tsx`) is the exception — it has its own sticky header with a back link instead of `TopAppBar`/`BottomNav`, since it's a full-screen chat view.
- **Profile detail overlay**: clicking a profile (from Discovery or Matches) sets `selectedProfileId` in app state; `RootAppStateOverlay` in `__root.tsx` renders `DetailedProfileView` on top of the current route (not a separate route/URL). `onMessage` in that overlay calls `startChat(id)` then navigates to `/matches/$contactId`.

## Conventions (from AGENTS.md — Lovable project rules)

- TypeScript only; functional React components; keep components small/focused; reuse existing components instead of duplicating UI or logic.
- Reuse the existing styling system (Tailwind + the design tokens above) — do not introduce another CSS framework or change colors/typography/spacing/visual design unless explicitly requested.
- Don't introduce new dependencies unless necessary; don't modify files unrelated to the requested task.
- This project is connected to Lovable: never rewrite published git history (no force-push, rebase, amend, or squash of already-pushed commits) — pushed commits sync back into the Lovable editor. Don't commit to `main` directly or create commits unless explicitly requested.
- Formatting/linting: Prettier (`printWidth: 100`, double-quote-off i.e. double quotes, semicolons, trailing commas — see `.prettierrc`) enforced through `eslint-plugin-prettier` in `eslint.config.js`; `@typescript-eslint/no-unused-vars` is turned off, but `tsconfig.json` has `strict: true` plus extra strictness (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitReturns`, etc.) — rely on `tsc`/editor type-checking, not lint, to catch those.
